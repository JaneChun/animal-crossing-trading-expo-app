# 제재 통지 · 이의 신청 설계

> 상태: 설계 (브레인스토밍 결과)
> 작성일: 2026-11-15
> 시안: https://claude.ai/artifact/RRybMR1VfHYg6qgvnKKHvv (Design 캔버스, 비공개). 현재 캔버스에 남은 보드가 확정 시안이다.
> 선행 작업: 관리자 기능(`feat/admin`, `feat/admin-user-activity` 브랜치, master 미병합). 이 설계는 그 위에서 진행한다.

## 1. 왜 하는가

지금은 신고 수만으로 계정이 자동 정지되고, 정지된 사용자는 "누적된 신고로 인해 활동이 제한되었습니다"라는 Alert만 본 뒤 로그아웃된다(`src/hooks/shared/useSuspensionGuard.ts`).

- 사용자는 **무엇을 위반했는지, 어떤 글 때문인지** 모른다. 이의를 제기할 창구도 약관의 이메일뿐이다.
- 운영 데이터(Reports 36건, 2025-12 ~ 2026-11)를 보면 자동 정지는 실제 위험과 맞지 않았다.
  - 위험한 글(마일티켓 원화 판매, 전화번호가 적힌 사이트 가입 대행 글, 타게임 계정 거래)은 신고가 몇 달에 흩어져 정지되지 않고 지금도 공개 상태다.
  - 반면 구걸·약속 번복처럼 가벼운 위반이 사흘 안에 몰린 사용자는 7일 정지된 것으로 보인다. 정지 이력이 남지 않아 확인할 수 없다.
  - 맞신고·보복성 신고가 있어, 자동 정지는 악용될 수 있다.
  - 신고의 3분의 2가 '기타'로 들어온다. 신고 카테고리가 실제 위반과 맞지 않는다.

목표는 **관리자가 판단해서 조치하고, 사용자는 무엇 때문에 어떤 조치를 받았는지 알고, 동의하지 않으면 앱 안에서 이의를 신청할 수 있게** 하는 것이다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 관리자가 위반 유형을 골라 게시글·댓글 숨김(경고)과 계정 정지를 건다.
- 사용자는 경고 화면과 정지 화면에서 위반 유형, 대상 글, 기간, 이의 신청 방법을 본다.
- 사용자는 조치 1건당 한 번 앱 안에서 이의를 신청하고, 결과(운영자 답변)를 앱에서 확인한다.
- 관리자는 이의 신청을 검토하고 답변과 함께 조치 유지 / 조치 취소를 정한다.
- 운영 정책을 사용자와 관리자가 같은 페이지에서 본다.

**비목표 (이번 범위 아님)**
- 매너 평가 확장(노쇼·약속 번복·구걸·기부 요구를 거래완료 전에도 리뷰로 남기기). 별도 작업으로 진행한다.
- 시스템 차원의 도배 자동 차단(게시 횟수 제한 등).
- 신고가 쌓인 글의 자동 숨김. 신고 규모가 커지면 나중에 검토한다.
- 앱 전체 문구의 "~해주세요" 띄어쓰기 정리(기존 코드). 이번에 새로 쓰는 문구만 맞춤법을 지킨다.
- 앱 안 일반 문의(1:1 문의 작성, 관리자 문의함). 설정의 '문의하기'는 지금처럼 메일로 둔다.

**실패 조건 (동작해도 실패로 본다)**
- 사용자에게 "90일", "1회·2회" 같은 내부 기준이 노출된다(통지·정책 페이지 모두).
- 신고 건수만으로 자동 정지가 계속 걸린다.
- 정지 이력이 남지 않아 사후에 무엇이 있었는지 확인할 수 없다.
- 이의 신청 결과가 사용자에게 전달되지 않는다.

## 3. 정책 (확정)

### 3-1. 위반 유형 6개

| 유형 | 심각도(관리자만 봄) |
|------|------|
| 사기 | 높음 |
| 현금·외부 거래 | 높음 |
| 개인정보·외부 연락 유도 | 높음 |
| 욕설/비방 | 중간 |
| 음란/부적절 콘텐츠 | 중간 |
| 광고/도배 | 낮음 |

- 노쇼·약속 번복·잠수·구걸·기부 요구는 제재 대상이 아니다. 매너 평가로 다룬다.
- 각 유형의 사용자용 설명과 ✕/✓ 예시는 시안의 '운영 정책 (사용자 · 관리자 공용)' 보드 문구가 기준이다.

### 3-2. 조치 단계 (관리자용 기준, 사용자에게 노출하지 않음)

| 최근 90일 위반 횟수 | 조치 |
|------|------|
| 1회 | 대상 글 비공개 + 경고 |
| 2회 | 7일 정지 |
| 3회 | 30일 정지 |
| 4회 이상 | 영구 정지 |

- 높음 등급은 첫 위반이라도 관리자가 바로 정지할 수 있다.
- 조치일로부터 90일이 지난 기록은 횟수에서 빠진다(관리자 화면에서 '만료'로 표시). 기록 자체는 지우지 않는다.
- 조치가 취소된(이의 신청 인용) 기록도 횟수에서 빠진다.
- 정지 바텀시트는 위 표로 계산한 권장 기간을 미리 선택하고 "최근 90일 위반 2회째로, 정책상 7일 정지를 권장합니다."처럼 이유를 보여 준다. 관리자는 바꿀 수 있다.

### 3-3. 자동 정지 폐지

- `functions/src/triggers/reports.ts`의 신고 수 기반 자동 정지(7일 3건 → 7일, 30일 7건 → 30일)를 없앤다.
- 신고는 계속 관리자 푸시(이미 구현됨)로 알리고, 관리자가 직접 판단한다.
- 기존 `needsAdminReview` / '검토 필요 유저' 목록은 기준이 사라진다. 새 기준은 "처리 대기 중인 이의 신청이 있는 사용자" + "처리되지 않은 신고가 있는 사용자"다(6장 참고).

## 4. 화면 (확정 시안 기준)

### 4-1. 사용자 화면

| 화면 | 시안 보드 | 핵심 |
|------|------|------|
| 경고 (1회 위반) | 대안 C 복사본 / 복사본 2 | 주황 칩 "운영 정책 위반 안내", "이 글은 비공개 처리되었습니다", 대상 글 카드, 해당 유형의 정책 카드(운영 정책 페이지와 같은 컴포넌트), 하단 "정책 위반이 반복되면 계정 이용이 제한될 수 있습니다." + [운영 정책 보기], [정책을 확인했습니다], [이의 신청] |
| 정지 (이의 신청 전) | 처분 | 빨간 칩 "계정 이용 제한 안내", "계정 이용이 제한되었습니다", 조치 내용(위반 유형·대상·제한 기간), 이의 신청 기한 안내, 진행 상황(조치 → 이의 신청 → 운영자 검토 → 결과 안내), [이의 신청] |
| 이의 신청 작성 | 이의 신청 작성 | 입력란 1000자, "이의 신청은 조치 1건당 한 번만 보낼 수 있습니다.", "조치가 취소되면 정지가 해제되고 비공개된 글이 다시 공개됩니다.", [제출하기] |
| 정지 (검토 중) | 이의 신청 작성 완료 & 운영자 검토 | 진행 상황에 운영자 검토 단계 "보통 3일 안에 검토합니다", 이의 신청 섹션(브랜드색 '검토 중' 칩), [이의 신청 완료](비활성), [로그아웃] |
| 정지 (결과 안내) | 결과 안내 | 진행 상황 모두 완료, 이의 신청(회색 '검토 완료' 칩), 결과 안내 카드(운영자 답변), "같은 조치에는 이의를 다시 신청할 수 없습니다." |
| 운영 정책 | 운영 정책 (사용자 · 관리자 공용) | 6개 유형 × (제목, 설명, ✕/✓ 예시). 일반 라우트에 두고 경고·정지 화면의 [운영 정책 보기]와 관리자 화면에서 연다 |

| 문의 내역 | (시안 없음) | 설정에서 진입. 탭 없이 한 목록에 경고·정지 기록과 각 이의 신청을 칩으로 구분해 보여 준다(예: [경고] [7일 정지] [검토 중] [검토 완료]). 행을 누르면 정지 화면과 같은 컴포넌트로 조치 내용·이의 신청·결과 안내를 보여 준다. 경고에 대한 이의 신청도 여기서 하고 결과도 여기서 본다 |

- 정지 중에는 지금처럼 앱 전체를 쓸 수 없다. 정지 화면에서 이의 신청과 로그아웃만 할 수 있다.
- 이의 신청이 받아들여지면(조치 취소) 정지가 바로 풀리므로 사용자는 정지 화면 대신 앱으로 들어간다. 이때의 안내 방식(토스트·푸시)은 구현자가 정한다.
- 이의 신청 결과가 나오면 푸시를 보내고, 누르면 문의 내역의 해당 항목으로 연결한다.
- **채팅으로 위반한 경우**도 조치 대상이다. 채팅 메시지는 숨기지 않는다. 경고 화면 제목은 "운영 정책 위반으로 경고를 받았습니다"로 쓰고, 대상 글 카드는 보여 주지 않는다. 정지 화면의 '대상' 행도 같은 방식으로 뺀다(구현자 판단으로 "채팅"이라고만 표시해도 된다).
- 정지되면 지금처럼 그 사용자의 다른 글(거래글·커뮤니티 글)도 모두 숨기고, 정지가 끝나면 다시 공개한다. 위반 대상 글은 정지가 끝나도 비공개로 남고, 조치가 취소될 때만 다시 공개한다.
- **이름**: 화면 이름은 '문의 내역'이지만, 앱 안 일반 문의 작성은 이번 범위가 아니다(2장 비목표). 지금은 조치와 이의 신청만 들어간다. 일반 문의가 생기면 같은 목록에 [문의] 칩으로 더한다.

- 이의 신청 상세는 유저 상세의 제재 이력 행과 '검토 필요 유저' 목록 행 두 곳에서 들어온다.
- 경고(글 숨김)도 같은 위반 유형 선택을 거친다. 기존 신고 상세의 [숨기기] 조치에 위반 유형 선택이 붙는다(구체 UI는 구현자가 정지 바텀시트 패턴을 따라 정한다).

### 4-3. 문구 규칙

- 사용자 대면 문구는 **합니다체 + "~해 주세요"**, 맞춤법대로 띄어 쓴다.
- 용어: '운영 정책'(띄어 씀), '운영자', '조치'(처분 대신), '이의 신청'(소명 대신), '조치 유지' / '조치 취소', 관리자 화면은 '유저', 사용자 화면은 '사용자'.
- 날짜: "2026.11.21 0시까지 (7일)".
- 차단 설명은 실제 동작과 같게: "차단한 사용자의 게시글은 보이지 않고, 그 사용자는 나에게 댓글과 채팅을 보낼 수 없습니다."

## 5. 필요한 변경 (방향만, 세부는 구현자)

- **조치(제재) 기록**: 경고·정지마다 기록을 남긴다. 최소 필드는 대상 유저, 조치 종류(경고/7일/30일/영구), 위반 유형, 대상 콘텐츠(컬렉션·글·댓글, 스냅샷), 근거 신고 목록, 조치일, 해제 예정일, 처리 관리자, 상태(유효/만료/취소). 저장 위치(최상위 컬렉션 vs 유저 하위)는 구현자가 정한다.
- **이의 신청**: 조치 1건당 1개. 신청 내용(1000자), 접수일, 상태(검토 중/검토 완료), 결과(유지/취소), 운영자 답변, 답변일.
- **정지 상태**: 지금의 `Users.report.suspendUntil`을 계속 쓸지, 조치 기록에서 계산할지 구현자가 정한다. 정지 화면은 현재 유효한 정지 조치와 그 이의 신청을 읽어야 한다.
- **Cloud Functions**: 자동 정지 제거, 관리자 조치 callable(경고·정지·정지 해제·이의 신청 결정), 정지 만료 스케줄러는 조치 기록과 맞춘다. 이의 신청 접수 시 관리자 푸시, 결과 결정 시 사용자 푸시.
- **보안 규칙**: 조치 기록은 본인 읽기 + 관리자 쓰기, 이의 신청은 본인 생성 1회 + 관리자 결정. CLAUDE.md 규칙대로 `firestore.rules`를 함께 고친다.
- **신고 카테고리**: `REPORT_CATEGORIES`를 3-1의 6개 유형(+기타)으로 바꾼다. 기존 신고 데이터의 카테고리 값 호환은 구현자가 처리한다.
- **경고 노출 시점**: 사용자가 다음에 앱을 열 때 경고 화면을 한 번 보여 주고, [정책을 확인했습니다]를 누르면 확인 처리한다. 푸시도 함께 보낸다.
- **이용약관 제5조**(`src/screens/TermsOfService.tsx`): 자동 정지 규칙("신고 3회 7일, 7회 30일")과 이메일 이의 제기 문구를 새 정책에 맞게 고친다. 내부 횟수 기준은 쓰지 않고 "위반이 반복되면 단계적으로 이용이 제한된다", "앱 안에서 이의를 신청할 수 있다" 수준으로 쓴다.
- **useSuspensionGuard**: Alert 대신 정지 화면으로 보낸다.

## 5-1. PR 나누기 (확정)

관리자 기능 PR(`feat/admin-user-activity`)이 먼저 병합되어야 한다. 그 위에 PR 3개로 나눈다. 앱 출시는 2·3번을 묶어서 한다.

1. **조치 기반 + 관리자 조치**: 위반 유형 6개와 신고 카테고리 교체, 조치 기록 모델, 자동 정지 제거, 관리자 경고·정지 callable, 정지 바텀시트(+위반 유형 선택), 유저 상세 제재 이력, 보안 규칙. 단독 배포 가능(사용자는 기존 Alert을 계속 본다).
2. **사용자 통지**: 정지 화면(Alert 대체), 경고 화면, 운영 정책 페이지, 이용약관 제5조.
3. **이의 신청**: 이의 신청 작성, 문의 내역, 관리자 이의 신청 상세(답변, 조치 유지/취소), 검토 필요 유저 목록 기준 변경, 결과 푸시.

## 6. 설계자 판단으로 정한 것 (사용자 확인 전)

브레인스토밍에서 사용자가 직접 정하지 않았고, 설계자가 정한 기준이다. 바꾸려면 사용자에게 확인한다.

- **이의 신청 기한**: 기간 정지는 해제일까지, 경고와 영구 정지는 조치일로부터 30일까지. 정지가 끝난 뒤에도 기한 안에 접수된 신청은 계속 검토하고, 결과는 문의 내역에서 본다.
- **정지 중 새 조치**: 조치는 각각 따로 기록한다. 실제 정지는 끝나는 날이 더 늦은 조치를 따른다. 정지 화면은 가장 최근 조치를 보여 주고, 이의 신청은 조치마다 따로 받는다. 한 조치가 취소되면 남은 유효 정지 조치 기준으로 정지 기간을 다시 계산한다.
- **[정지 해제]와 [조치 취소]의 차이**: 관리자의 [정지 해제]는 기간만 앞당겨 끝낸다. 위반 기록은 유효로 남아 횟수에 포함되고, 대기 중인 이의 신청도 그대로 검토할 수 있다. 횟수에서 빠지는 것은 이의 신청을 인용한 [조치 취소]뿐이다.
- **'만료' 표시**: 관리자 화면에서만 쓰는 말이다. 조치일로부터 90일이 지나 횟수에서 빠졌다는 뜻이다.

## 7. 구현자 판단으로 남긴 것

- 조치·이의 신청 데이터 구조와 컬렉션 이름.
- 이의 신청 인용 시 사용자 안내 방식(토스트 / 푸시 / 둘 다).
- '검토 필요 유저' 목록의 정렬과 섹션 구분(이의 신청 대기 / 미처리 신고).
- 경고(글 숨김) 시 위반 유형을 고르는 UI의 정확한 배치.
- 기존 사용자 중 정지·숨김 이력이 있는 데이터의 이전 여부(현재 정지 중인 유저는 0명).
- 문의 내역 화면의 행 디자인(관리자 제재 이력의 '칩 하나' 행을 사용자용으로 맞추는 것을 권장).
- 작업 기준 브랜치: 관리자 작업은 `feat/admin-user-activity`에 있고 master에 병합되지 않았다. 병합 후 진행할지, 그 브랜치에서 이어서 진행할지는 계획 단계에서 사용자에게 확인한다.
