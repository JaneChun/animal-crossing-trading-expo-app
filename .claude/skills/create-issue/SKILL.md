# /create-issue — 버그 메모를 `/fix-issue`용 GitHub 이슈로 만들기

메모나 설명에서 버그를 골라내고, 코드를 탐색해 재현 경로·관련 코드·검증 기준을 채운 이슈를 만든다.
여기서 만든 이슈의 **검증 기준**은 `/fix-issue`가 그대로 체크리스트로 쓴다.

## Argument Parsing

| 입력 | 처리 |
|---|---|
| 파일 경로 (`.md` 등) | 파일을 읽는다. 경로에 공백이 있으면 따옴표로 감싼다 |
| 그 외 텍스트 | 버그 설명으로 본다 |
| 비어 있음 | 버그 메모나 설명을 달라고 묻는다 |

## Execution

### Step 1: 항목 분류

입력의 모든 항목을 아래 표로 분류해 대화에 보여준다.

| 분류 | 기준 | 이슈 생성 |
|---|---|---|
| A. 바로 처리 가능 | 코드 수정만으로 해결되고, iOS 시뮬레이터·Android 실기기 스크린샷으로 결과를 확인할 수 있다 | 대상 |
| B. 검증 방법이 다름 | 코드로 해결되지만 스크린샷으로는 확인할 수 없다 (로직, 푸시 알림, 앱 종료 후 상태 등) | 사용자가 고르면 대상 |
| 제외 | 디자인 에셋 제작, 콘솔·외부 서비스 설정, 신규 기능, 설계 결정이 필요한 작업 | 대상 아님 |

- 분류마다 이유를 한 줄로 붙인다.
- 어떤 항목을 이슈로 만들지 사용자에게 확인받는다.

### Step 2: 중복 확인

```bash
gh issue list --state open --limit 100 --json number,title
```

같은 현상을 다루는 열린 이슈가 있으면 그 번호를 보여주고, 새로 만들지 기존 이슈에 덧붙일지 묻는다.

### Step 3: 코드 탐색

이슈마다 아래를 찾는다.

1. **화면과 진입 경로**: 증상이 나오는 화면 컴포넌트(`src/screens/`, `src/components/`)와, 홈에서 그 화면까지 가는 경로
2. **원인 후보 코드**: 레이아웃이면 `KeyboardAvoidingView`·safe area·`snapPoints`·고정 높이, 로직이면 해당 훅·스토어·서비스
3. **공통 컴포넌트 여부**: 원인 후보가 `src/components/ui/` 아래에 있거나 여러 곳에서 import되면, 사용처를 모두 나열한다
   ```bash
   grep -rln "<컴포넌트명>" src --include='*.tsx'
   ```
4. **함께 확인할 화면**: 같은 패턴(예: 키보드 위 인풋)을 쓰는 다른 화면

메모의 표현과 코드의 이름이 다르면(예: 메모 "일괄 저장" ↔ 코드 "일괄 추가") 어떻게 해석했는지 초안에 적는다.

### Step 4: 초안 작성과 확인

`${CLAUDE_SKILL_DIR}/templates/issue.md` 형식으로 이슈마다 초안을 쓴다.

- 제목: `[iOS] ...`, `[Android] ...`, 양쪽이면 `[공통] ...` 접두어 + 현상을 한 문장으로
- 입력 요소(인풋, 키보드 위 버튼)가 있는 화면은 검증 기준에 **키보드를 올린 상태** 확인을 반드시 넣는다
- 검증 기준의 마지막 줄은 항상 `iOS·Android 스크린샷 첨부`

초안 전체를 대화에 보여주고 생성 여부를 확인받는다.

### Step 5: 이슈 생성

본문을 스크래치 폴더에 파일로 쓰고 생성한다.

```bash
gh issue create -l bug -t "<제목>" -F <본문 파일>
```

생성된 이슈 번호와 URL을 표로 보고한다.

## Rules

- 저장소가 public이다. 사용자 닉네임·제보자 정보·내부 URL·토큰은 이슈에 쓰지 않는다.
- 사용자 확인 없이 `gh issue create`를 실행하지 않는다.
- 라벨은 `bug`만 붙인다.
- 코드를 탐색해 확인한 파일만 관련 코드에 적는다. 추측한 경로는 쓰지 않는다.
- 원인을 단정하지 않는다. 관련 코드는 "원인 후보"이며, 원인 확정은 `/fix-issue`가 한다.
- 대화 출력과 이슈 본문은 한국어로 쓴다.
